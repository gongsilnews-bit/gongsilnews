## 0. 선행 확인 — Vercel 와일드카드 (완료)

어제 회의록 4-5의 선행 확인 항목이었다. 바깥에서 두드려 확인했다.

| 확인 | 결과 |
|---|---|
| 와일드카드 DNS | 정상 — 무작위 서브도메인이 Vercel IP로 떨어진다 |
| 프로젝트 도메인 등록 | 정상 — `X-Matched-Path: /sites/[subdomain]` 로 미들웨어까지 도달 |
| 없는 주소 | 404 (설계대로) |
| 발급된 4개 주소 | 전부 200 |

**주소를 새로 발급해도 Vercel에 따로 등록할 필요가 없다.** 일괄 발급이 성립한다.

다만 어제 커밋한 일괄 발급 스크립트는 `--write` 없이 미리보기만 돌아간 상태였다.
대상 7명 중 4명은 이미 있고, 1명(`borikwang`)은 발급 대기, 2명은 정보설정(상호·등록번호)이
비어 있어 건너뛴다. **표시광고법상 필수 항목이 빈 광고가 나가므로 이 건너뛰기 규칙은 유지한다.**

## 1. 부동산 요금제 개명

### 1-1. 배경

관리자 드롭다운은 `무료 / 공실뉴스부동산 / 공실등록부동산` 이었는데,
**'공실등록부동산'이라는 상품은 실제로 팔지 않는다.** 판매 페이지에서 파는 것은
`/study` 의 **공실스터디**(월 3만 원)다. 이름만 옛날 것으로 남아 있었다.

코드가 실제로 가르던 것은 이랬다.

| 코드값 | 옛 이름 | 기사 작성 | 공실 등록 | 레벨 |
|---|---|---|---|---|
| `news_premium` | 공실뉴스부동산 | 가능 (월 한도) | 한도 내 | 3 |
| `vacancy_premium` | 공실등록부동산 | **차단** | 무제한 | 4 |

해당 요금제를 쓰는 회원이 **0명**이라 지금이 바꾸기 가장 싼 시점이었다.

### 1-2. 결정 사항

| # | 안건 | 결정 |
|---|------|------|
| 1 | 이름 | 공실등록부동산 → **공실스터디부동산** |
| 2 | 코드값 | `vacancy_premium` → **`study_premium`**. 이름만 바꾸고 옛 코드값을 두면 여섯 달 뒤에 그것이 공실스터디인 줄 알 사람이 없다 |
| 3 | 한도 정책 키 | `LIMIT_REALTOR_VACANCY_*` → `LIMIT_REALTOR_STUDY_*`. 저장된 값(50/20)은 SQL 로 옮긴다 |
| 4 | 표시 순서 | 무료 → **공실스터디부동산** → **공실뉴스부동산** (드롭다운·등급별 한도 설정 표 공통) |
| 5 | 권한·한도·레벨 | **이번에는 건드리지 않는다.** 이름만 바꾼다 |

### 1-3. 건드리지 않은 것

- `공실등록` 이라는 **기능·메뉴 이름** (공실등록 폼 제목, 모바일 홈 메뉴 등). 요금제가 아니다
- `vacancy_basic` — realty_admin 에 남아 있는 별개 코드값
- `docs/architecture/*` 4건 — 현재 동작을 설명하는 문서인데 아직 옛 이름을 가리킨다. **따로 정리해야 한다**

### 1-4. 보류 — 두 등급의 권한이 사실상 같다

판매 페이지를 열어보니 두 상품이 거의 같은 것을 약속하고 있다.

| | 공실뉴스부동산 | 공실스터디 |
|---|---|---|
| 가격 | 월 30,000원 | 월 30,000원 |
| 공실 등록 | 월 20건 | 월 20건 |
| 기사 송고 | 월 4건 | **월 4건** |
| 고유 혜택 | 공동중개망, 유튜브 마스터클래스, 광고 영업권 | VOD 전 과목, **경공매 열람** |

그런데 코드는 `study_premium` 의 기사 작성을 막고 있다. **판매 문구와 코드가 어긋나 있다.**

제안은 두 등급을 "권한은 같고 입구만 다른 형제 등급"으로 못 박고, 권한 판정을 한 곳으로
모으는 것이었다. **이번 회의에서는 결정하지 않았다.** 다음 안건으로 남긴다.

## 2. 기능 권한을 등급·회원별로 열고 닫기

### 2-1. 배경

최고관리자가 회원 등급별 기본 한도를 정하는 화면은 **이미 있었다** —
`회원관리 → [등급별 한도 설정]` 탭. 다만 찾기 어려운 자리에 있었고(목록 필터 다섯 개와
같은 줄, 회색, 배지 없음), 다루는 것이 **숫자 두 개(공실 수·기사 수)뿐**이었다.

기능 자체의 on/off 는 다섯 파일에 하드코딩돼 있어 최고관리자가 바꿀 수 없었다.

### 2-2. 결정 사항

| # | 안건 | 결정 |
|---|------|------|
| 1 | 판정의 주인 | **회원 칸.** 등급은 가입·승인·요금제 변경 때 기본값을 내려줄 뿐이다 |
| 2 | 회원별 예외 | **허용.** 최고관리자가 등급과 상관없이 한 사람씩 열고 닫는다 |
| 3 | 기존 회원 | 오픈 전이라 지킬 예외가 없다. 전부 등급 기본값으로 맞춘다 |
| 4 | 요금제 만료 | **요금제로 받은 권한은 요금제가 끝나는 날 같이 닫힌다.** 무료 회원에게 관리자가 직접 열어준 것은 끝날 요금제가 없으므로 그대로 열려 있다 |
| 5 | 이번에 넣을 권한 | 기사 배너광고 · 기사 공실배너 · 물건접수웹페이지 |

### 2-3. 기본값

| 등급 | 기사 배너광고 | 기사 공실배너 | 물건접수웹페이지 |
|---|---|---|---|
| 일반회원 | ✗ | ✗ | ✗ |
| 부동산회원 (무료) | ✗ | ✗ | ✗ → **3장에서 켜기로 결정** |
| 공실스터디부동산 | ✓ | ✓ | ✓ |
| 공실뉴스부동산 | ✓ | ✓ | ✓ |
| 비즈니스회원 | ✓ | ✗ | ✓ |

비즈니스회원의 공실배너를 끈 이유 — 공실 등록 한도가 3건이라 기사에 붙일 매물이 거의 없다.

### 2-4. 구조

```
point_settings          PERM_{등급}_{권한}  = 0/1   ← 등급 기본값
members.can_*                                       ← 판정의 주인
planDefaults()                                      ← 등급 → 회원 값 복사, 한 곳
isPermissionAlive()                                 ← 켜져 있는가 + 요금제가 살아 있는가
```

`planDefaults()` 는 회원 수정·부동산 승인·비즈니스 승인·소급 적용 네 곳이 같이 쓴다.
전에는 같은 매핑이 네 군데 복사돼 있었다.

### 2-5. 화면에서 감추는 것만으로는 막히지 않는다

**기사 배너광고는 지금까지 서버 검사가 한 줄도 없었다.** 편집 화면에서 입력칸을 감춰도
저장 요청을 직접 보내면 그대로 들어온다. 배너가 만들어지는 곳(`saveAuthorBanner`)과
기사에 붙는 곳(`updateArticlesAdSettings`) 두 길목을 서버에서 막았다.

## 3. 물건접수웹페이지 — 전원 개방, 기능으로 등급 나누기

### 3-1. 어제 결정을 뒤집는다

어제 회의 8번은 **"문은 요금제가 연다"** 였다. 무료는 503 일시중지 화면을 본다.
오늘은 반대로 간다 — **문은 전원 열고 안에서 기능을 나눈다.**

회원이 7명인 지금 "결제해야 열립니다"는 팔 물건이 없는 것과 같다. 일단 손에 쥐여주고
좁게 만드는 쪽이 전환이 빠르다. `can_homepage` 스위치는 **최고관리자의 강제 차단용**으로
남기고 기본값만 뒤집는다.

### 3-2. 손대지 않아도 이미 벌어져 있는 차이

홈페이지는 그 사람이 올린 매물과 기사를 그대로 끌어온다. 요금제 한도가 그대로 페이지에
반영된다.

| | 무료 | 유료 |
|---|---|---|
| 공실 등록 한도 | 3건 | 20 / 50건 |
| 월 기사 작성 | 0건 | 10 / 20건 |
| → 홈페이지 추천공실 | 최대 3건 | 20건 |
| → 홈페이지 기사·칼럼 섹션 | **자동으로 사라짐** (내용 없는 섹션은 숨는다) | 있음 |

### 3-3. 결정 사항

| # | 안건 | 결정 |
|---|------|------|
| 1 | 접수 폼 | **무료도 그대로 쓴다.** 빼려면 헤더 버튼·히어로 CTA·모바일 하단바·앵커 내비를 전부 전화 걸기로 갈아끼워야 하는데, 그만한 값이 없다 |
| 2 | 문의관리(CRM) | **무료도 그대로 쓴다** |
| 3 | 히어로 슬라이드 | 무료 **1장** / 유료 3장 |
| 4 | 푸터 `powered by 공실뉴스` | 무료 **남김** / 유료 **숨김** |
| 5 | 접수 시 사진 첨부 | 무료 **불가** / 유료 최대 5장 |
| 6 | 접수 건수 | **제한하지 않는다** |
| 7 | 주소 발급 | 정보설정(상호·등록번호)을 채운 회원에게만. 규칙 유지 |

### 3-4. 왜 접수 건수를 제한하지 않는가

| | 크기 |
|---|---|
| `crm_customers` 행 1개 | 약 1KB |
| `crm_logs` 행 1개 | 약 1KB |
| **접수 사진 1장** | **약 200KB** |

사진 한 장이 텍스트 100건치다. 중개사 100명이 매달 20건씩 1년을 받으면 텍스트는 48MB,
사진은 14GB다. **건수를 막아서 아끼는 것은 48MB인데, 대신 임대인이 폼을 눌렀을 때
"접수를 받을 수 없습니다"가 뜬다. 그 손님은 중개사가 아니라 공실뉴스가 이상하다고
생각한다.**

그래서 제한은 **건수가 아니라 사진**에 건다. 마침 `사진 첨부`는 이미 중개사가 켜고 끄는
접수 항목이므로, 무료는 그 스위치를 잠그면 된다. 사진이 없어도 접수는 끝까지 된다.

### 3-5. 유료였다가 무료로 내려간 회원

**기존 사진은 지우지 않는다.** 중개사 고객의 자료이고, 재결제하면 그대로 돌아와야 한다.
새 접수에서만 사진 단계가 빠진다.

## 4. 이름 — 물건접수장 → 물건접수웹페이지

`물건접수장`이라는 말이 **상품 전체를 그 안의 한 섹션 이름으로 부르고** 있었다.

| 쓰는 자리 | 이름 |
|---|---|
| PC·모바일 관리자 메뉴, 편집기 제목, 공유 문구 | **물건접수웹페이지** |
| 주소 입력 라벨 | **웹페이지 주소** |
| 접수 건의 유입 경로 값 | **물건접수웹페이지** |

**공개 페이지의 `물건 접수` 버튼들은 그대로 둔다.** 상품 이름이 아니라 방문한 손님에게
누르라고 하는 말이다.

## 5. 규모를 키웠을 때 — 돈이 아니라 코드가 걸린다

### 5-1. 회원 1만 명 · 10년 누적

| | 10년 누적 |
|---|---|
| 접수 건수 | 2,400만 건 |
| 접수 텍스트 | 약 48GB |
| 접수 사진 | 7,200만 장 · 약 14.4TB |
| **저장 비용** | 10년째 월 30~40만 원 / 누적 2,000만 원대 |
| 같은 기간 매출 | 360억 원 |

**저장 비용은 매출의 0.06%다. 비용 때문에 기능을 깎을 이유는 없다.**

### 5-2. 그보다 먼저 걸리는 것

**① 접수 폼에 아무 방어가 없다.** `submitPropertyIntake` 에 횟수 제한도, 중복 검사도,
자동입력 방지도 없다. 이름과 연락처만 있으면 그대로 저장된다. 무료로 전원에게 열면
공개 폼이 회원 수만큼 늘어나고 표적도 그만큼 늘어난다. **가장 급하다.**

**② 고객문의 목록이 한 중개사 1,000건에서 조용히 틀어진다.** 지금 `getCustomers` 는
그 부동산의 고객을 전부 불러오고, 그 id 를 전부 한 줄에 넣어 로그를 조회하며,
로그는 1,000건까지만 본다.

| 접수 누적 | 증상 |
|---|---|
| 수백 건 | 목록이 느려진다 |
| **1,000건** | 로그 제한을 넘은 고객의 "최근 문의"가 비어 뒤로 밀린다 |
| 수천 건 | id 를 전부 붙인 요청이 길이 제한을 넘어 조회가 실패한다 |

어제 회의 9-2에서 "DB 컬럼 추가 없음"으로 정했던 부분이다. 회원이 7명일 때는 맞는
판단이었지만, **`last_contact_at` 컬럼 하나가 위 세 가지를 한 번에 없앤다.**

**③ 미들웨어가 서브도메인 요청마다 DB를 친다** (`cache: 'no-store'`). 홈페이지 1만 개면
방문 한 번마다 쿼리 한 번이다. 짧은 캐시가 필요하다.

### 5-3. 개인정보 보유기간 — 10년의 진짜 문제

접수 폼은 동의를 받고 있지만 **보유기간이 없다.** 개인정보처리방침은 **회원 탈퇴 시 파기**만
규정하는데, **접수한 임대인은 회원이 아니다.** 탈퇴할 계정이 없으니 이름과 연락처가
영원히 남고, 지울 방법도 코드에 없다.

2,400만 건이면 기간 제한 없이 들고 있는 개인정보가 그 규모가 된다. 유출 사고가 나면
규모가 그대로 과징금이 된다. **용량보다 이쪽이 훨씬 비싸다.**

| 대상 | 결정 |
|---|---|
| 접수 사진 | **2년 후 삭제** |
| 접수자 이름·연락처 | **3년 후 마스킹** (`홍○○ / 010-****-1234`) |
| 접수 기록·통계 | 영구 보존 |
| 중개사가 고객으로 등록한 건 | 제외 (계속 보관) |

마스킹이 삭제보다 낫다. 중개사에게 "몇 년에 몇 건 받았다"는 기록은 남고, 우리는
들고 있으면 안 될 것만 버린다.

**이번에는 문구만 넣는다.** 실제로 지우는 배치 작업은 다음 안건이다.

## 6. 오후에 정한 것들

### 6-1. 게시판 권한 레벨을 맞바꾼다

게시판 쓰기·읽기 권한 레벨이 옛 서열 그대로였다.

| 레벨 | 전 | 후 |
|---|---|---|
| 3 | 공실뉴스부동산 | **공실스터디부동산** |
| 4 | 공실등록부동산 | **공실뉴스부동산** |

**공실뉴스부동산이 최상위다.** 요금제 사다리와 게시판 레벨이 반대로 가 있었다.

지금 게시판 열한 개 중 4레벨을 쓰는 것이 없고, 3레벨은 두 유료 등급이 모두
통과하므로 **들어올 수 있는 사람은 그대로다.** 앞으로 공실뉴스부동산 전용
게시판을 만들 때 4레벨을 쓰면 된다.

코드 기본값도 옛 서열(공실스터디 50/20이 위)로 남아 있어 함께 맞췄다.
DB 값이 우선이라 지금 동작은 그대로지만, 두면 새 환경에서 다시 뒤집힌다.

### 6-2. 등급별 한도 설정이 실제로 적용되게

**저장 버튼이 장식이었다.** 정책만 `point_settings` 에 저장되고 회원에게는
내려가지 않아, 정책은 공실 50인데 회원은 20, 같은 등급 안에서도 사람마다
3/0 과 20/10 이 섞여 있었다.

| # | 안건 | 결정 |
|---|------|------|
| 1 | 저장하면 | **그 등급 회원에게 바로 내려간다** |
| 2 | 개별로 손봐 둔 회원 | **건드리지 않는다** |
| 3 | 가르는 기준 | "지금 값이 **바뀌기 전 기본값**과 같은가" 하나. 컬럼을 더 두지 않는다 |
| 4 | 체크박스 | 뜻이 바뀐다 — **개별 조정까지 전부 되돌리기** |

### 6-3. 같은 규칙을 회원 편집 화면에도

회원별 기사 한도를 50 으로 고쳐도 저장하면 4 로 돌아갔다. **바로 위
회원구분이나 요금제를 한 번이라도 건드리면** 그 등급 기본값으로 11개 값
(한도 2 · 권한 9)을 아무 말 없이 덮어썼기 때문이다. 두 칸이 위아래로 붙어
있어 요금제나 기간을 만지다 보면 걸린다.

6-2 와 같은 기준을 화면에도 적용했다. 손봐 둔 값은 등급을 바꿔도 지킨다.

> 등급 표가 서버(`planDefaults`)와 화면(`gradeDefaults`) 두 곳에 있다.
> **한쪽만 고치면 어긋난다.**

### 6-4. 기능 차등을 여섯 가지로 늘린다

3-3 에서 정한 셋에 셋을 더했다.

| 항목 | 무료 | 유료 |
|---|---|---|
| 첫 화면 장수 | 1장 | 3장 |
| 공실뉴스 표시 숨김 | ✗ | ✓ |
| 접수 사진 첨부 | ✗ | ✓ |
| **로고 올리기** | ✗ (상호 글자만) | ✓ |
| **첫 화면 유튜브 영상** | ✗ (사진까지) | ✓ |
| **SNS 링크** | ✗ | ✓ |

**일부러 뺀 것** — 첫 화면 배경사진, 테마 색상, 접수 항목(구해요·희망금액·메모),
추천공실·기사 섹션. 무료 페이지가 명함에 박을 수 없을 만큼 초라해지면 아무도
쓰지 않고, 안 쓰면 붙잡아 둘 것도 없다.

잠긴 자리마다 무엇이 열리는지 적어 둔다. 막기만 하면 왜 안 되는지 몰라 문의가 온다.

### 6-5. 접수 서식을 두 경우에 맞게 가른다

`구하는 물건이 있어요` 가 내놓는 서식을 그대로 쓰고 있었다. 관리비·방/욕실·
면적·해당층까지 물었다. **내놓는 사람은 자기 물건을 보고 적으면 되지만 구하는
사람은 아직 물건이 없다.**

| | 구해요에서 묻는 것 |
|---|---|
| 남긴 것 | 매물 종류 · 거래 구분 · 희망 금액대 · 희망 지역 · 입주 희망일 · 기타 요청사항 |
| 뺀 것 | 관리비 · 방/욕실 · 면적 · 해당층/전체층 · 사진 |

- **금액은 최저~최고를 고르게 한다.** 만원 단위로 적으라 하면 거기서 창을 닫는다.
  거래 구분에 따라 갈린다 — 매매는 `희망 매매가`, 전세는 `희망 보증금`,
  월세·단기는 `희망 보증금` + `희망 월세`. 월세 보증금은 자릿수가 달라 목록을 따로 둔다
- **지역은 번지를 묻지 않는다.** 같은 검색창을 쓰되 시·군·동 세 토막만 남긴다.
  손으로 치게 하면 지역 이름이 제각각 적혀 한 동네 문의만 모아 보기 어려워진다
- 2걸음 안내 문구도 갈라준다. 구하는 손님에게 "물건을 홍보할 수 있습니다" 라고
  말하고 있었다

접수 완료 화면의 사진 안내는 **사무실 전화번호**로 바꿨다. 사진은 이미 선택
항목이고 무료에서는 받지도 않는다. 접수가 끝난 자리는 전화를 걸기에 가장 좋은
자리다 — 손님은 방금 무엇을 맡겼는지 기억이 생생하고, 중개사도 그 건으로 바로
상담할 수 있다.

### 6-6. 폰에서 만지는 느낌

| 안건 | 결정 |
|---|---|
| 하단 가로 띠 | **없앤다.** 오른쪽 아래 세로 버튼으로 — 아래에서 위로 전화 · 접수 · 즐겨찾기 · 맨위로 |
| 띠가 물고 있던 74px | 되돌려준다 |
| 맨위로 | 600px 넘게 내려갔을 때만 |
| 목록 롤오버 | 기사 줄은 바탕이 밝아지고 매물 카드는 떠오른다. 손가락 화면에서는 걸지 않는다 |
| 누른 뒤 기다림 | **회색 스켈레톤 막**으로 가린다 |

**화면 전환(View Transition)은 붙였다가 껐다.** 누른 카드 사진이 다음 화면
사진으로 자라나는 움직임인데, 실제 폰에서 두 가지가 걸렸다.

1. 전환은 **새 화면이 다 준비된 뒤에야** 시작한다 — 느릴 때는 여전히 눌러도
   아무 일이 없다. 고치려던 문제가 그대로 남는다
2. 출발과 도착 사진의 모양이 다르다(카드 4:3 ↔ 상세 가로 띠·16:9). 억지로 이으면
   찌그러지며 늘어난다. `animation: none` 이 사라지는 동작까지 꺼 **잔상**도 남았다

`viewTransition.ts` 는 지우지 않고 왜 껐는지 적어 두었다. 도착 화면의 사진 모양을
카드와 맞출 수 있게 되면 다시 켜볼 만하다.

### 6-7. 바탕화면에 깔기

중개사 홈페이지를 손님 폰 바탕화면에 아이콘으로 남긴다. **명함은 서랍에
들어가지만 바탕화면 아이콘은 폰을 열 때마다 보인다.**

| # | 안건 | 결정 |
|---|------|------|
| 1 | 앱 이름 | **중개사 상호.** '공실뉴스' 로 깔리면 의미가 없다 — manifest 를 주소마다 따로 만든다 |
| 2 | 아이콘 | 로고가 있으면 그 로고, 없으면 **테마색 바탕에 상호 첫 글자** |
| 3 | 로고 파일 | 주소만 넘기지 않고 **직접 받아와 심는다.** 그림 만드는 쪽에서 실패하면 알 길이 없어 아이콘이 통째로 깨진다 |
| 4 | 서비스워커 | **아무것도 가로채지 않는다.** 캐시를 돌려주기 시작하면 중개사가 고쳐도 손님 폰에 옛 화면이 남는다 |
| 5 | 아이폰 | 설치창을 띄울 방법이 없다. `공유 → 홈 화면에 추가 → 추가` 를 시트로 안내한다 |
| 6 | 이미 깔았으면 | 버튼이 보이지 않는다 |

**실제 폰에서 확인해야 한다.** 배포된 https 주소에서만 설치 신호가 온다.

### 6-8. 색과 글자

- 중개사 페이지에서 여는 **기사 말머리 · 공실 금액 · 연락처 버튼 · 해시태그**를
  그 중개사의 테마색으로. 포털 공실열람·공실뉴스와 같이 쓰는 화면이므로 **색을
  밖에서 넣어주는 통로만 뚫고**, 안 주면 지금 파란색 그대로 둔다
- 메뉴 글자를 진한 검정 17px 로. 흐린 회색이면 눌러도 되는 줄 모른다
- 로고와 상호를 한 단계씩 키운다 (36·48·60px)
- 푸터 `admin` 은 홈페이지 편집이 아니라 **관리자 첫 화면**으로 — PC 는
  `/realty_admin`, 폰은 `/m/admin/dashboard`

### 6-9. 고객문의 목록 — `last_contact_at`

5-2 ② 에서 미뤘던 것을 오늘 했다.

목록을 그릴 때마다 고객을 전부 불러오고, 그 id 를 한 줄에 붙여 `crm_logs` 를
조회한 뒤 앱에서 정렬했다. 로그는 1,000건까지만 봤다.

**컬럼 하나로 셋 다 없앤다.** 조회가 두 번에서 한 번으로 줄고, 1,000건 제한도
id 를 붙인 긴 요청도 사라진다.

갱신은 **DB 트리거**가 한다. 기록을 넣는 곳이 코드 다섯 군데라 한 곳만 빠뜨려도
그 고객이 조용히 뒤로 밀리고, 나중에 스크립트로 넣을 때도 마찬가지다.

**페이지 나눔은 아직 하지 않는다.** 지금 화면은 전부 받아 브라우저에서 검색·탭을
거르므로, 페이지를 나누려면 그것들을 서버로 옮겨야 한다. 이 컬럼이 들어가면
급하지 않으니 접수가 실제로 쌓이는 것을 보고 판단한다.
